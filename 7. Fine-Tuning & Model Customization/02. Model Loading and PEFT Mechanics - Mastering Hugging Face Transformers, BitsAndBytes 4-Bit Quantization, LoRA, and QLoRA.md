## 📌 Executive Overview & Spoon-Fed Real-World Analogy

In the previous topic, we learned that full fine-tuning a 7-billion or 8-billion parameter model requires over **100 GB of GPU VRAM**—far beyond the capacity of consumer hardware or budget cloud GPUs. How do AI engineers fine-tune state-of-the-art models on a single consumer GPU (like an RTX 4090 with 24GB or an inexpensive cloud instance)?

The answer lies in two revolutionary technologies working in tandem: **Quantization (BitsAndBytes NF4)** and **Parameter-Efficient Fine-Tuning (PEFT / LoRA)**.

```
+----------------------------------------------------------------------------------------------------+
|                               THE "POST-IT NOTE ON A TEXTBOOK" ANALOGY                             |
+----------------------------------------------------------------------------------------------------+
|                                                                                                    |
|  1. FULL FINE-TUNING (Rewriting the Entire Book):                                                  |
|     Imagine you want to customize a 1,000-page medical encyclopedia.                               |
|     • Full fine-tuning means erasing and rewriting all 1,000 pages by hand.                        |
|     • It requires an enormous desk (100GB+ VRAM) to hold all drafts, ink bottles, and editors.    |
|     • If you make a mistake, you risk ruining the original knowledge (catastrophic forgetting).   |
|                                                                                                    |
|  2. QUANTIZATION (Shrinking the Textbook):                                                         |
|     Before doing anything, you compress the heavy encyclopedia into a pocket-sized paperback.      |
|     • Each number in the model is converted from a 16-bit decimal into a compact 4-bit code.       |
|     • Memory footprint drops from 16 GB down to 4 GB with virtually zero loss of comprehension.    |
|                                                                                                    |
|  3. LoRA / PEFT (Sticking Post-It Notes on Selected Pages):                                        |
|     Instead of rewriting the book, you LOCK (FREEZE) all the original pages completely.            |
|     • You stick small transparent Post-It notes on the key chapters.                              |
|     • When someone asks a question, they read the page through the Post-It note, which adds your   |
|       specialized adjustments on top of the original text!                                         |
|     • Your Post-It notes only contain 0.2% of the book's total content, requiring almost no desk   |
|       space (only 6 GB total VRAM for training!).                                                  |
+----------------------------------------------------------------------------------------------------+
```

## 1. 📂 Hugging Face Model Repository Anatomy

Before writing code, let’s understand what is actually inside a model repository on the Hugging Face Hub (e.g., `meta-llama/Meta-Llama-3-8B` or `mistralai/Mistral-7B-v0.1`):

```
my-llm-repo/
├── config.json                 <-- Blueprint: Architecture, dimensions, heads, layers
├── generation_config.json      <-- Default inference settings (temperature, top_p, EOS tokens)
├── model.safetensors.index.json<-- Shard map: Which layers are in which safetensors file
├── model-00001-of-00004.safetensors <-- Actual frozen matrix weights (safe binary format)
├── tokenizer.json              <-- Fast tokenizer vocabulary and BPE merge rules
├── tokenizer_config.json       <-- Chat templates, padding tokens, special token IDs
└── special_tokens_map.json     <-- Definitions for <|im_start|>, <|im_end|>, <unk>, <eos>
```

### Key Parameters in `config.json` Demystified:
- `hidden_size` ($d_{\text{model}}$): The width of the neural network (e.g., $4,096$).
- `num_hidden_layers`: How many stacked transformer blocks exist (e.g., $32$).
- `num_attention_heads`: Query heads for self-attention (e.g., $32$).
- `num_key_value_heads`: Key/Value heads. If smaller than `num_attention_heads`, the model uses **Grouped-Query Attention (GQA)** to save inference VRAM.
- `intermediate_size`: Width of the SwiGLU feed-forward layer (e.g., $14,336$).

## 2. 💻 Loading Models into Python: The Modern Transformers Pipeline

Here is how you load a tokenizer and model cleanly in Python using the official `transformers` library:

```python
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM

model_id = "meta-llama/Meta-Llama-3-8B-Instruct"

# 1. Load the Tokenizer
tokenizer = AutoTokenizer.from_pretrained(
    model_id,
    trust_remote_code=True,
    padding_side="right"  # SFT training requires right padding for causal masks
)

# Crucial Gotcha: Ensure pad_token is defined
if tokenizer.pad_token is None:
    tokenizer.pad_token = tokenizer.eos_token
    tokenizer.pad_token_id = tokenizer.eos_token_id

# 2. Load the Model in 16-bit Precision (Requires ~16GB VRAM just for weights)
model = AutoModelForCausalLM.from_pretrained(
    model_id,
    torch_dtype=torch.bfloat16,  # Use bfloat16 for Ampere+ GPUs (A100, RTX 3090/4090)
    device_map="auto"           # Automatically distribute layers across available GPUs
)
```

> [!NOTE]
> Setting `padding_side="right"` is critical during SFT training so that padding tokens do not alter the positional indices of the attention mask for the causal sequence. For batch *inference*, `padding_side="left"` is standard.

## 3. 📉 Understanding Quantization: FP32 vs. FP16 vs. INT8 vs. 4-Bit NF4

Floating-point precision dictates how many bits represent each parameter:

```
+----------------------------------------------------------------------------------------------------+
|                                    WEIGHT PRECISION COMPARISON                                     |
+----------------------------------------------------------------------------------------------------+
|  Precision | Bits | Memory per 1B Params | 8B Model Size | Description                             |
+----------------------------------------------------------------------------------------------------+
|  FP32      |  32  | 4.0 GB               | 32.0 GB       | Standard single-precision float (legacy)|
|  FP16/BF16 |  16  | 2.0 GB               | 16.0 GB       | Half-precision (industry default)       |
|  INT8      |   8  | 1.0 GB               |  8.0 GB       | 8-bit integer quantization (LLM.int8()) |
|  NF4       |   4  | 0.5 GB               |  4.0 GB       | 4-bit NormalFloat (QLoRA standard)      |
+----------------------------------------------------------------------------------------------------+
```

### Why NormalFloat4 (NF4) is Superior to Standard INT4
Traditional INT4 divides the numerical range linearly into 16 evenly spaced bins. However, neural network weights follow a **zero-mean Gaussian (bell curve) distribution**: most weights cluster near $0.0$, with very few outliers at $\pm 1.0$.

Linear quantization wastes bins on empty regions. **NF4 (NormalFloat4)** calculates 16 quantile bins where each bin has an equal probability mass under a standard normal distribution. This information-theoretically minimizes quantization error!

### Double Quantization (DQ)
In standard 4-bit quantization, scaling factors (absmax constants) are stored every 64 weights, taking $0.5$ bits per parameter. **Double Quantization** quantizes the quantization constants themselves, cutting overhead from $0.5$ bits down to $0.127$ bits per parameter—saving roughly $373\text{ MB}$ of VRAM on an 8B model.

## 4. ⚙️ Configuring BitsAndBytes 4-Bit QLoRA in Code

To load an 8B model into only ~5GB of VRAM, use `BitsAndBytesConfig`:

```python
from transformers import BitsAndBytesConfig
import torch

bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,                         # Activate 4-bit precision loading
    bnb_4bit_quant_type="nf4",                 # Use NormalFloat4 distribution
    bnb_4bit_use_double_quant=True,            # Apply nested double quantization
    bnb_4bit_compute_dtype=torch.bfloat16      # Dequantize to BF16 during forward pass computations
)

# Load model in 4-bit QLoRA mode
model = AutoModelForCausalLM.from_pretrained(
    model_id,
    quantization_config=bnb_config,
    device_map="auto"
)
```

## 5. 🔬 The Mathematics of LoRA (Low-Rank Adaptation)

Published by Edward Hu et al. (Microsoft, 2021), **LoRA** hypothesizes that weight updates during adaptation have a **low intrinsic rank**.

```
+---------------------------------------------------------------------------------------+
|                                LoRA FORWARD PASS EQUATION                             |
+---------------------------------------------------------------------------------------+
|                                                                                       |
|                       h = x · W₀  +  (x · A · B) · ( α / r )                          |
|                                                                                       |
|   Where:                                                                              |
|   • W₀ ∈ ℝ^(d × k)  : Frozen base model weight matrix (e.g. 4096 × 4096)               |
|   • A  ∈ ℝ^(d × r)  : Down-projection adapter initialized ~ 𝒩(0, σ²)                  |
|   • B  ∈ ℝ^(r × k)  : Up-projection adapter initialized to ZERO                       |
|   • r               : Rank hyperparameter (typically 8, 16, or 32)                   |
|   • α (Alpha)       : Constant scaling factor (typically 2 × r, e.g., 32)            |
+---------------------------------------------------------------------------------------+
```

### The Initialization Invariance Property
Notice that matrix $B$ is initialized to **all zeros**:
$$\Delta W = B \times A = 0 \times A = 0$$
At step 0 of training, the adapter outputs exactly zero. The model begins training behaving **100% identically to the original base model**, with no sudden performance collapse!

## 6. 🎯 Target Module Selection: What Should You Adapt?

A transformer block contains attention projection matrices and MLP feed-forward matrices. Which ones should LoRA hook into?

```
Transformer Layer:
├── Self-Attention
│   ├── q_proj (Query)      <── Attention queries
│   ├── k_proj (Key)        <── Attention keys
│   ├── v_proj (Value)      <── Attention values
│   └── o_proj (Output)     <── Attention output projection
└── MLP (SwiGLU)
    ├── gate_proj           <── Gating activation
    ├── up_proj             <── Expansion
    └── down_proj           <── Projection back to d_model
```

### Target Module Strategies Comparison

| Strategy | Target Modules | Trainable % (8B Model) | Best For |
|---|---|---|---|
| **Attention-Only** | `["q_proj", "v_proj"]` | $\approx 0.04\%$ | Basic tone/persona tweaks, minimal VRAM |
| **Full Attention** | `["q_proj", "k_proj", "v_proj", "o_proj"]` | $\approx 0.08\%$ | Conversational dialogue |
| **All-Linear (Recommended)** | `["q_proj", "k_proj", "v_proj", "o_proj", "gate_proj", "up_proj", "down_proj"]` | $\approx 0.52\%$ (at $r=16$) | **State-of-the-Art performance** for complex reasoning, SQL, coding |

## 7. 🔌 Integrating PEFT with PyTorch in Code

```python
from peft import LoraConfig, get_peft_model, prepare_model_for_kbit_training

# 1. Prepare quantized model for gradient checkpointing and training
model = prepare_model_for_kbit_training(model)

# 2. Configure LoRA parameters
peft_config = LoraConfig(
    r=16,                                    # Rank: Lower = fewer params, Higher = more expressivity
    lora_alpha=32,                           # Scaling: Standard rule of thumb is 2 * r
    lora_dropout=0.05,                       # Regularization dropout on LoRA layers
    bias="none",                             # Do not train bias terms
    task_type="CAUSAL_LM",                   # Autoregressive language modeling
    target_modules=[
        "q_proj", "k_proj", "v_proj", "o_proj",
        "gate_proj", "up_proj", "down_proj"
    ]
)

# 3. Wrap base model with PEFT adapters
peft_model = get_peft_model(model, peft_config)

# 4. Print Trainable Parameters
peft_model.print_trainable_parameters()
# Output:
# trainable params: 41,943,040 || all params: 8,072,200,192 || trainable%: 0.5196%
```

## 8. ⚠️ Common Traps & Gotchas in QLoRA Setup

1. **Trap 1: Forgetting to Cast Norm Layers to FP32**:
   - Quantizing LayerNorm / RMSNorm weights to 4-bit causes severe numerical instability and loss spikes (`NaN`).
   - *Fix*: `prepare_model_for_kbit_training()` automatically casts norm layers to 32-bit floating point.
2. **Trap 2: Using BFloat16 on Unsupported Hardware**:
   - GPUs older than NVIDIA Ampere (such as the free Google Colab Tesla T4 or Volta V100) do not have native BFloat16 tensor cores. Specifying `compute_dtype=torch.bfloat16` will trigger errors or slow down execution.
   - *Fix*: Use `torch.float16` on T4 GPUs; use `torch.bfloat16` on RTX 3090/4090 and A100/H100.
3. **Trap 3: Missing End-Of-Sequence (EOS) Token in Generation**:
   - If `tokenizer.pad_token == tokenizer.eos_token`, ensure your loss collator does not mask out the EOS token, or the model will generate endless repetitive loops!

## 11. 🧠 Self-Assessment Knowledge Check

<details>
<summary><strong>Question 1: In LoRA matrix decomposition $W = W_0 + B \cdot A$, why is matrix $B$ initialized to all zeros while matrix $A$ is initialized with random Gaussian noise?</strong></summary>

<br>

**Answer**:
If both matrices $A$ and $B$ were initialized with random values, their product $\Delta W = B \cdot A$ would be non-zero at step 0. This would inject immediate random noise into the model's weights, corrupting its pre-trained knowledge before training even starts!

By initializing $B = 0$:
$$\Delta W = B \cdot A = 0 \cdot A = 0$$
At step 0, the adapter contributes exactly zero, meaning the model begins training with its exact original pre-trained capabilities. Initializing $A$ with random Gaussian noise breaks symmetry, allowing backpropagation to compute valid gradients during the first backward pass.
</details>

<details>
<summary><strong>Question 2: What is the purpose of the scaling factor $\frac{\alpha}{r}$ in LoRA, and how does varying $\alpha$ affect training?</strong></summary>

<br>

**Answer**:
The scaling factor $\frac{\alpha}{r}$ scales the magnitude of the adapter's update $\Delta W$ relative to the base weights $W_0$. When you change the rank $r$ (e.g., from $r=8$ to $r=16$), the scaling factor prevents you from having to retune your learning rate from scratch.

A standard convention is to set $\alpha = 2 \times r$ (which results in a constant multiplier of $2.0$). Higher values of $\alpha$ give greater weight to the adapter's updates, while lower values keep the model closer to its base behavior.
</details>

<details>
<summary><strong>Question 3: Why is NormalFloat4 (NF4) quantization significantly more accurate than standard uniform 4-bit integer (INT4) quantization for deep neural network weights?</strong></summary>

<br>

**Answer**:
Weights in pre-trained neural networks are distributed according to a zero-mean normal distribution (Gaussian bell curve). Most weights are clustered tightly between $-0.5$ and $+0.5$, with very few outliers at the extremes.

Uniform INT4 divides the entire range into 16 equal bins, dedicating too many bins to sparsely populated extreme ranges and too few bins to the dense center. **NF4** computes 16 quantile bins such that each bin has an equal probability mass under a normal distribution, minimizing information loss.
</details>

<details>
<summary><strong>Question 4: What is the difference between setting <code>target_modules=["q_proj", "v_proj"]</code> vs. <code>target_modules="all-linear"</code> in LoRA?</strong></summary>

<br>

**Answer**:
- `["q_proj", "v_proj"]`: Adapts only the Query and Value projections in the self-attention mechanism. It trains very few parameters ($\approx 0.04\%$), but research shows it has limited capacity for complex domain adaptation or reasoning tasks.
- `"all-linear"`: Attaches LoRA adapters to all 7 projection matrices (Query, Key, Value, Output, Gate, Up, and Down). It trains roughly $\approx 0.4\% - 0.5\%$ of parameters. Empirical benchmarks (including the QLoRA paper) demonstrate that adapting all linear layers yields substantially higher task performance.
</details>

<details>
<summary><strong>Question 5: Why must the tokenizer have <code>padding_side="right"</code> during Supervised Fine-Tuning with causal language models?</strong></summary>

<br>

**Answer**:
Causal language models use a causal attention mask that prevents tokens at position $i$ from attending to future tokens at position $j > i$.

If you pad on the left during training, the padding tokens shift the absolute positional encodings of the actual input text, interfering with the attention mechanism and causal loss computation. Padding on the right ensures that all real tokens maintain their natural positional indices starting at 0, while padding tokens at the end are easily ignored using the attention mask.
</details>
